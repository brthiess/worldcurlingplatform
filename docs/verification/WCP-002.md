## Delivered boundary

An assigned scorekeeper can start a scheduled four-player game with resolved opponents, enter/correct a live end, record known/unknown hammer for that selected end, and see persisted public changes. The HTTP adapter and editor share the application command. Game locking, current grant/source checks, expected version, normalized command receipts and transactional before/after audit protect accepted state. Duplicate delivery returns the original receipt; mismatched identifier reuse and stale versions cannot overwrite scores.

End-specific hammer survives corrections to other ends. Public current hammer is explicitly tied to its end and remains unknown unless that end has a known fact. The public game view also lists recorded per-end hammer. No automatic hammer progression is inferred. New migrations are uniquely named `0003_wcp002_live_scoring_commands.sql` and `0004_wcp002_end_hammer_context.sql`; the second adds the reviewed end context without changing already-applied migration contents.

The editor initializes from actual accepted end values, labels unsent/saving/uncertain/saved states, keeps a draft and exact pending request in actor/game-scoped tab storage, and retains them through reload/reconnection. Uncertain requests block further edits until an explicit identical retry confirms the result. Stale edits retain values while the operator loads and compares the accepted version. Public refresh keeps the chosen draw, visible scorecards and keyboard focus. Public reads use a consistent PostgreSQL snapshot and preserve actual end-number columns.

No game confirmation, confirmed-result correction, downstream advancement, lineup management, partner provisioning or full offline synchronization is implemented or claimed by this ticket. See [scoring API contract](../api/scoring.md).

## Failures found and fixed

- Initial `npx tsx` ran before `npm ci` completed and reported the executable unavailable; the actual red domain run then used the already installed matching runtime and failed on the missing module. The worktree's own clean installation subsequently completed normally.
- Review caught single game-level hammer being overwritten by corrections to an older end, and initial form values defaulting to `0–0` despite stored `0–1`. End-scoped facts and initial accepted values were fixed and independently asserted.
- Browser checks found that disabling the inherited refresh button dropped keyboard focus. The button now retains its DOM focus while `aria-disabled` and the click guard prevent overlapping manual refresh.
- A development error locator matched both the application alert and Next.js's route announcer. Added the useful accessible label `Score entry error` and selected that exact alert.
- Rapid development-suite repetitions reached the retained credential rate limit (**429**); no limit was relaxed and no auth bypass was introduced. The final production build/start and complete suite passed with real sessions.
