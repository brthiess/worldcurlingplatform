# Manual entries and roster boundaries

WCP-006 provides organizer manual entry, without opening self-entry, capacity reservations, payment collection or ranking eligibility. Every write requires the current signed-in actor's administrator grant or organizer grant for the entry's edition. A player-account link provides no organizer authority. The browser adapter checks the configured request origin. Domain commands perform the same resource checks within their transaction.

`GET /api/v1/entries` returns assigned divisions and entries. `POST /api/v1/entries` accepts `{id, requestId, version:0, entry}`. `GET /api/v1/entries/:id?version=N` reads a reviewed version; `POST /api/v1/entries/:id` updates with `{requestId, version, entry}`. Existing legacy entries at version zero have no recorded lineup and can acquire their first version. A request ID belongs to one actor and exact command; exact retries return the original immutable version, conflicting reuse and stale edits return 409. Authorization is rechecked before replay.

The entry payload contains `divisionId`, `name`, `coreKnown`, `corePlayerIds`, and `members`. A member has `playerId`, `role` (`core`, `alternate`, `coach`, `substitute`), `position` and `participation` (`declared`, `defaulted`). Core membership is separate from members present at the event. An absent regular player stays in `corePlayerIds`; an event guest uses `substitute`. Five rotating regular players are all core. Complete men's/women's four-player cores have four or five people, and a mixed-doubles core has two. Unknown/incomplete cores are allowed with `coreKnown:false` and no inferred team identity.

`newPlayers:[{id,name,provisional}]` creates account-free sport records in the entry transaction. The records must occur in this entry, player foreign keys are checked, and names never merge identities. Mark an unresolved possible duplicate provisional. Identified complete core membership automatically creates/reuses the unique discipline plus unordered-player-set team, independently of name/position/season/coach/alternate/substitute changes. The discipline comes from the entry's division. There is no team approval/publication gate or lineage.

Optional `teamId` asserts that exact existing identity; mismatched core/discipline is rejected. Optional `registrationId` links the matching team's season registration. Neither changes its roster. `registerSeason:{season:"2026-27",version:0}` explicitly creates an initial season roster containing regular core, alternates and coaches, excluding temporary substitutes. Amendments to an existing season registration require a platform administrator and its reviewed version. Event organizer permission alone does not grant control over an existing season roster. Later P-02 team-season representation grants entry/payment authority, not official season/ranking roster control.

The relational tables are `team` / `team_core_member`, `season_registration` / `season_roster_version` / `season_roster_member`, and `event_lineup_version` / `event_lineup_core` / `event_lineup_member`. Every entry version references one atomic audit record and the exact linked season-roster version. Core/history mutation triggers reject updates and deletes. Entry saves never overwrite older roster versions. Team identity equality does not confer WCTRS eligibility or entitlement.

The trusted shared read boundary is exported from `src/modules/entries/entries.ts`:

```ts
readEventLineup(reader: Pick<PoolClient, "query">, entryId: string, version?: number): Promise<EventLineup | null>
```

An omitted version reads the entry's current version. It returns `entryId`, `version`, `status`, `teamId`, `registrationId`, `registrationVersion`, `name`, `coreKnown`, `recordedAt`, and ordered `members` with the fields above plus public name/identity status. No recorded lineup (including legacy version zero) returns null. The caller owns authorization/public-admission checks and any transaction required to read with game state consistently. A later game default/override must reference **entry ID plus lineup version**, preserve absent/unknown evidence, and never mutate season/core membership. Declared/defaulted rosters do not independently verify which people delivered stones in a game.

Public reads are `/api/v1/public/teams[/:id]`, `/api/v1/public/entries/:id`, and `/api/v1/public/events/:id/entries`. Team identities and sport season rosters are public without an extra team approval gate; event entry details/listings require an admitted, published event. Public projections omit actor IDs, request IDs, command digests, account links, emails and claims. Public player projections now include `identityStatus` so unresolved records can be labelled honestly. Public views are `/teams`, `/teams/:id`, `/entries/:id`, and links from the existing event score view.
